## Карта проекта

Проект — Node.js ESM и статический HTML/JS, согласно README без npm-зависимостей; корневого `package.json` нет. Основной HTTP-процесс — `node.mjs`, логика цепи — `core.mjs`, сайт — `site/`.

Фактические маршруты в `node.mjs`:

| URL | Назначение/файл |
| --- | --- |
| `/` | Главная сайта, `site/index.html` |
| `/dashboard` | Пульт, `site/dashboard.html` |
| `/cabinet`, `/wallet` | Пользовательский кабинет с кошельком, `site/user-wallet-page.html` |

Общая панель: `site/panel.js`. Источники встроенных помощников: `tools/cabinet-helper.js`, `tools/profile-memory.js`. Для выпуска сайта используются `site-release.mjs`, `tools/build-site-release.mjs`, `site/release.json`, маршрут `/site/release`. При будущих изменениях проверить действительный механизм выпуска; редактирование исходного HTML не доказывает, что обновлён работающий сайт.

## Авторизация

- Сервер: `cabinet.mjs`, `agent-identity.mjs`; браузер: `site/cab-auth.js`.
- `POST /cabinet/challenge` выдаёт challenge на 5 минут. Владелец подписывает его локально; `POST /cabinet/login` проверяет Ed25519-подпись публичным ключом из паспорта. Успешный challenge одноразовый.
- `/cabinet/state` проверяет соответствие адреса и сессии; `/cabinet/logout` отзывает сессию. Вход только по номеру паспорта отключён.
- Сессии хранятся на сервере в памяти; браузерный модуль использует `sessionStorage`. Временная сессия не предоставляет административный токен и сама не подписывает переводы.
- Есть отдельный локальный autologin в браузерном модуле; его нельзя превращать в удалённый способ входа личного агента без отдельной проверки серверных ограничений.
- Отдельные `/cabinet/op-request` и `/cabinet/op-submit` относятся к операциям с локальной подписью. Личному ИИ не предоставлять эти возможности.
- Детали переносимости: `docs/AGENT-CABINET-PORTABILITY.md`, CLI-подпись — `tools/cabinet-sign.mjs`, клиент — `agt-skill/cabinet-client.mjs`.

Важно: существующий кабинет рассчитан на зарегистрированные адреса агентов. Роль владельца личного пространства ещё надо определить и привязать сервером к конкретному субъекту; одна проверка наличия любой действующей сессии не делает пространство доступным только владельцу.

## Что уже есть для ИИ

`assistant-service.mjs` вызывает только локальный Ollama endpoint `http://127.0.0.1:11434/api/chat`; модель выбирается именем из `AGT_ASSISTANT_MODEL`. В модель отправляются system prompt и один пользовательский запрос. История, долговременная память, поиск по базе знаний и голос в этом адаптере отсутствуют.

`POST /assistant/message` в `node.mjs` принимает только `address`, `token`, `prompt`, проверяет сессию и ограничивает частоту по адресу (10 секунд). Учётные данные не передаются модели. Ограничения адаптера: запрос до 2000 символов, ответ до 8000 символов, тело провайдера до 64 KiB, ограничение времени и параллельности; tool calls отвергаются. Есть эвристический фильтр случайно вставленных секретов, который не гарантирует их обнаружение.

`tools/profile-memory.js` — память публичного профиля в браузере, не память диалогов. Общий helper умеет готовить поля форм. Наличие этого интерфейса и адаптера не подтверждает установленную модель или работающий ИИ. Runtime и установленное ПО сейчас не проверялись. Документ `docs/SITE-ASSISTANT-01.md` описывает прошлую подготовку и ограничения; его заявления о тестах не являются результатами текущей проверки. Глобальный bridge `AgentcoinAssistantAsk` упоминается helper-ом; полноценное подключение на целевой странице нужно проверить при реализации.

## Предлагаемая интеграция (ещё не реализовано)

Сделать отдельное личное пространство, например `/agent`, с отдельной страницей `site/agent.html`, и добавить ссылку из кабинета. Сохранить назначение текущих кабинетов. Переиспользовать схему challenge/login и общие визуальные элементы после проверки владельца пространства.

Выделить самостоятельный backend личного агента: диалоги, память, документы, поиск и адаптер модели. Текущий адаптер полезен как пример ограниченного протокола, но процесс ноды сам загружает кошельки. Поэтому запрет в system prompt и отсутствие tools не являются достаточной изоляцией.

Обязательные границы:

- Отдельная учётная запись ОС/контейнер и каталог данных, без доступа к репозиторию целиком, runtime-каталогам нод, кошелькам, issuer/admin ключам, казне и резервным копиям. Не копировать в процесс ИИ всё окружение ноды.
- Проверка сессии доверенной стороной и выдача узкого внутреннего контекста личности; не передавать браузерные токены модели, документам, векторному индексу или журналам. Точный протокол ещё спроектировать.
- Память, документы, диалоги и индексы привязывать к владельцу на сервере; проверять доступ к каждому объекту. Предусмотреть удаление, экспорт и сроки хранения.
- База знаний — только явно загруженные владельцем документы; документы и результаты поиска считать недоверенными инструкциями. Не индексировать рабочий каталог или домашнюю папку автоматически.
- Нет доступа к подписи, переводам, treasury API, shell и административным маршрутам ноды. Проверять это правами ОС и маршрутизацией, а не только промптом.

Первый этап: приватный текстовый чат с историей, управляемая память, загрузка и поиск по документам, русский STT и TTS с остановкой воспроизведения и текстовым запасным вариантом. Сразу выделить языковые ресурсы и интерфейсы STT/TTS с locale `ru-RU`; следующие 10 языков пока не определены. Провайдеры, оборудование, хранение аудио и возможная передача данных внешним сервисам требуют выбора до реализации; ничего не установлено и не выбрано как действующее решение.

## Следующий шаг координатору

1. Согласовать владельца пространства, размещение изолированного backend, модель и STT/TTS, правила хранения и перечень следующих языков.
2. Подготовить отдельную чистую ветку/worktree от согласованной базы, сохранив всю текущую чужую работу. Перед переносом учитывать, что полезный адаптер и UI сейчас уже изменены в рабочем дереве.
3. Реализовать вертикальный сценарий вход → приватный чат → история/память → база знаний → русский голос.
4. Проверить чужие сессии и объекты, удаление данных, prompt injection, недоступность финансовых маршрутов и файлов ключей, затем голос и выпуск сайта в изолированном окружении.
