# CABINET-01: переносимый кабинет и управление нодами

Реализовано как прикладной слой, без изменения консенсуса, адресов и истории цепи.
Владелец управляет сайтом, кодом, административными маршрутами и выдачей паспортов.
Агент хранит ключ в собственной среде; кабинет и нода приватный ключ не получают.
Отдельная полная нода агенту необязательна. IP не является идентификатором владельца.

## Что переносится

- `profile.json`: зашифрованные Ed25519/BIP39 секреты, AES-256-GCM + scrypt.
- `profile.json.passport.json`: публичный сертификат, подписанный издателем.
- Отдельная зашифрованная резервная копия профиля, сохранённая в другой среде.
- Конфигурация доверия: сеть, genesisHash, fingerprint издателя, проверенный URL ноды.

`agentId` детерминирован сетью, адресом и публичным ключом. У той же копии ключа
тот же агент; количество процессов не создаёт независимых владельцев. Баланс
определяется цепью адреса, а не наличием паспорта в локальном JSON.
Сессии ноды временные: после рестарта нужно войти заново, ключ перевыпускать не нужно.
Установка и точные stdin-схемы: [agt-skill/SKILL.md](../agt-skill/SKILL.md).

## API и безопасность

`GET /identity/meta` публикует ключ издателя, его fingerprint, network/audience и роль.
На ноде-издателе `POST /identity/challenge` принимает только `{address,pub,handle}`.
Агент проверяет network/action/audience/fingerprint/адрес/срок и подписывает локально.
`POST /identity/register` принимает `{challengeId,signature}`, возвращает сертификат.
Дочерняя нода принимает его через `POST /identity/import {passport}` только при
заранее настроенном доверии издателю. Произвольная самоподписанная запись отвергается.

`POST /cabinet/challenge {address}` выдаёт отдельный login challenge (5 минут).
`POST /cabinet/login` принимает адрес, challengeId, message в поле nonce и подпись.
Верификация использует только публичный ключ; наличие ключа в wallets.json не нужно.
Успешный challenge одноразовый. К чужой ноде/действию подпись неприменима.
`/cabinet/state` требует token + соответствующий address. Сессия не является
подписью транзакции и не даёт глобальный admin token.
Номер паспорта не является секретом: вход по seqStr отключён, нужен ключ.

Веб-кабинет принимает только публичный паспорт и готовую подпись.
Он не просит seed, privKey или пароль; торговая форма, полагавшаяся на серверный
ключ, убрана. Skill работает отдельно и проверяет pin, сеть и genesisHash перед
регистрацией/входом. Для внешних нод разрешён HTTPS; HTTP только loopback.
Пароли вводятся через stdin из защищённого канала, не через аргументы процесса.

## Настройка оператора и дочерней ноды

На основной ноде по умолчанию `AGT_IDENTITY_ROLE=issuer`.
Ключ выдачи лежит в `DATA_DIR/identity/identity-issuer.json` (0600); это собственный
служебный ключ оператора, а не ключ агента. Сохранить его в защищённой резервной
копии вместе с публичным реестром. Потеря/смена issuer key меняет доверие.

Для реплики:

```text
AGT_IDENTITY_ROLE=replica
AGT_TRUSTED_ISSUERS_FILE=<абсолютный путь к JSON-массиву PEM публичных ключей>
AGT_PASSPORT_ISSUER_FINGERPRINT=sha256:<fingerprint оператора>
AGT_IDENTITY_AUDIENCE=<уникальное имя этой ноды>
AGT_ADMIN_MODE=token
AGT_ADMIN_TOKEN=<через локальное секретное хранилище>
```

Ключи доверия устанавливаются оператором через отдельный доверенный канал;
страница незнакомой ноды не доказывает правильность её fingerprint.
У реплики есть собственный служебный ключ для контекста login; Skill различает
ключ login-ноды и ключ издателя паспорта. Выдача паспортов на реплике закрыта.
Право на публикацию сайта или операторские API паспорт не предоставляет.

## Восстановление и смена ноды

1. Восстановить профиль из отдельного encrypted backup в новый файл; проверить
   правильность пароля и совпадение публичного адреса через `info`.
2. Перенести публичный сертификат рядом с восстановленным профилем.
3. Через `cabinet-client connect` проверить новую ноду с теми же network/genesis
   и закреплённым издателем. Ключ профиля не изменяется.
4. Выполнить `login`: сертификат импортируется, новый challenge подписывается
   локально. Открыть state и сверить адрес/баланс/высоту цепи.
5. Старую среду закрывать после проверки восстановленной копии. Две активные
   копии одного ключа имеют одинаковые полномочия — изолируйте доступ к ним.

Если утрачены все копии ключа/seed/backup и пароль, оператор не может восстановить
владение. Распределённое хранение самой цепи этого не исправляет. Падение процесса
ноды не уничтожает локальный профиль агента.

## Ноды и сайт

Watchdog проверяет дешёвый `/health`, уничтожает зависшие HTTP-запросы по deadline,
различает responding/stale/overloaded/down и не убивает отвечающую ноду за старый
блок. Неизвестный владелец порта запрещает спавн; wrapper проверяется до остановки.
Отложенная попытка не считается выполненным рестартом. Health-check выбирает
точную задачу/host/data-dir; удалённому узлу не передаёт локальный admin token.

`/life` кеширует совместимую проверку цепи на 30 секунд с ключом chain-ref + length
+ tipHash; это не строгий аудит исторических транзакций. Same-height reorg обновляет
кеш. `syncAll` single-flight; изменение локальной цепи во время await откладывает
сетевой commit, не затирает новый блок и не штрафует пира.

`GET /network/nodes` возвращает эту ноду и только явно настроенные цели мониторинга.
`AGT_MONITOR_TARGETS_FILE` — путь к локальному JSON:

```json
[{"name":"B","url":"http://127.0.0.1:9341"},{"name":"C","url":"http://127.0.0.1:9342"}]
```

Добавить TS с фактическим локальным tailnet URL в этом файле; не публиковать его в git.
Сервер проверяет фиксированные цели с таймаутом и single-flight/cache; посетители
не могут передать URL. Сайт не обращается к localhost удалённого посетителя.
`stale_tip` — давно не было блока; `lower_observed_height` — ниже максимальной
наблюдаемой высоты. Ни то ни другое само по себе не доказывает падение или лучшую
цепь: канон выбирается по валидной накопленной работе.

## Внедрение на рабочем Windows-хосте (Codebuff)

1. Зафиксировать фактические PID, commandline, data-dir, задачи, высоты/tip и логи.
   Сохранить локальные AGIP-17 core.mjs, spore.mjs, конфигурацию и данные вне git.
   Не применять reset/clean, массовое убийство node.exe или сброс цепи.
2. До замены TS-wrapper сохранить настоящий IP в ignored `data-agtx/ts-bind.txt`
   либо `AGT_TS_BIND`. Новая обёртка и watchdog не угадывают адрес; без конфигурации
   показывают ошибку и не запускают/не убивают TS. B/C привязаны к loopback.
3. Назначить роли издателя/реплик и установить pins. Сохранить issuer key.
4. Остановить адресно только обновляемый процесс, дождаться освобождения порта,
   запустить штатную обёртку. Обновлять по одной ноде; сверить собственный data-dir.
5. Выполнить `tools/nodes-autostart.cmd verify`; административная установка должна
   реально устранить legacy-дубликаты и создать недостающие задачи. Без прав
   сообщить конкретный блокер. Правка скрипта не доказывает установку задачи.
6. Проверить `/health`, `/life`, `/network/nodes`, кабинет и публичный admin barrier
   с другой машины; затем 15 минут наблюдать рост/сходимость цепи и рестарты.
7. Опубликовать в issue commit → команда → результат → ограничения, без секретов.

## Приёмка и границы

`node --test test/cabinet-portability.mjs` запускает два реальных изолированных
процесса ноды, локальную регистрацию/подпись, доверенный импорт/вход, отрицательные
подписи и replay, перезапуск обеих нод, encrypted restore и настоящий Skill-клиент.
Проверяет отсутствие агентских секретов на диске сервера и admin API 403.
Сетевые тесты используют синтетические профили, без production-денег.

Автоматический отзыв/ротация ключей, social recovery, multisig recovery и консенсусная
паспортная квалификация голосов пока не реализованы. Публичный сертификат не создаёт
право голоса сверх существующих правил. Предложения и голосование не публикуют код
автоматически: выпуск сайта остаётся у владельца. Новая система не объявляет
существующие SDK-01 escrow/data и SEC-01 audit-задачи закрытыми.

У старых node-wallets ключ остаётся у держателя ноды; новый профиль не удаляет и
не мигрирует такие кошельки автоматически. Legacy send подписывает имеющийся
локальный PEM без `/tx/sign`, но старый plaintext файл требует отдельной миграции.
Windows ACL задаются владельцем системы; POSIX mode не является их заменой.

## Одобренный выпуск сайта

После приёмки доработки владелец выполняет `node tools/build-site-release.mjs`,
проверяет diff `site/release.json` и публикует файлы вместе с manifest. ID выпуска
по умолчанию зависит от содержимого; повторный ID с другим содержимым нода не примет.
`node tools/build-site-release.mjs --check` в CI запрещает забыть хеши/общий panel.js.
`GET /site/release` показывает действующий выпуск и хеши для сравнения разных нод.
Старый пофайловый кеш site-live больше не используется; данные не удаляются.

Сначала обновить backend нод до API v2 из подготовленной ветки, затем публиковать
новый канонический frontend в main. Старые процессы с прежним безусловным site-sync
не умеют проверять совместимость manifest — их нужно обновить адресно до публикации.
Это предотвращает появление нового кабинета на старом API. Рестарт по одной ноде
с сохранением данных и проверкой `/identity/meta`, `/site/release`, `/health`.

Конфигурация собственной ноды создаётся через `tools/agent-node-setup.mjs` согласно
Skill. Локальные peers/bootstrap/monitor не наследуют топологию владельца. Пустой
bootstrap означает отсутствие настроенного сетевого соединения, а не успешный sync.

Операторский прежний кабинет с выставлением/отменой ордеров сохранён отдельно:
`GET /operator/cabinet`, за административным барьером. Он использует старые
кошельки ноды. Публичный `/cabinet` работает с новым локальным профилем; его
сессия не открывает операторский кабинет. Изменение main 39014c1 сохранено.

Операторский HTML поддерживает прямой loopback в local-режиме. В token-режиме
страница и операционные запросы требуют отдельно настроенного операторского
клиента/прокси с x-admin-token; кабинетная сессия этим токеном не является.
Форма seqStr и неиспользуемое поле privKey из операторского HTML удалены.
