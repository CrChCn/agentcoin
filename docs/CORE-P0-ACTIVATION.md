# CORE-P0 — единый консенсус-верификатор и план активации

Task: **CORE-P0** (из issue #1, комментарий 6250846229 и LEDGER-20261018-01 FINAL 6251064114).

## Что закрыто (один verifier на всех путях)

`validateBlockAgainstChain()` — единственный сетевой верификатор блоков. Все входы
используют его: HTTP `/block/submit` и `/mine` (`commitMinedBlock`), WS-приём,
линейный синк (`sync.mjs`), adoptFork, `bc.validate(true)` (полная историческая
сверка теперь делегирует тому же верификатору — «унифицировать verifier» из аудита).

При активации (`block.height >= порога`) верификатор ДОБАВЛЯЕТ к legacy-правилам:

| дефект из аудита | правило |
|---|---|
| «проверяет сумму только первого COINBASE» extra-эмиссия | ровно ОДИН coinbase (`multiple_coinbase`), amount ∈ (0, blockReward] |
| «пропускает авторизацию всех COINBASE/AGENT_REWARD_POOL» | `system_spend_forbidden` — с `AGENT_REWARD_POOL` (и любой будущей системной ролью) расход запрещён; COINBASE зачисляет только награду |
| «Merkle доверяет переданному txid» | канонический `txid === txDigest(tx)` для coinbase и каждой tx (`coinbase_txid_not_canonical` / `txid_not_canonical`) — merkle привязан к содержимому |
| «reward label не связывает содержимое» | награда зачисляется последовательно в replay балансов; лишний зачисления невозможен (см. пункт выше) |
| «неверный chainId» | `header.chainId === CHAIN_ID` (`chainId_mismatch`) |
| «не делает последовательную проверку расходов/replay» | ПОСЛЕДОВАТЕЛЬНАЯ бухгалтерия в порядке tx внутри блока: `insufficient_funds_block`; уникальность txid в блоке (`duplicate_txid_block`), `(from,nonce)` (`duplicate_nonce_block`) и всей цепи (`tx_replay_in_chain`); конечные суммы (`tx_bad_amount`) |

Опциональные инкрементальные контексты для тяжёлых вызовов (adoptFork, sync):
`opts.knownTxids` (Set txid префикса) и `opts.prefixBalances` (балансы префикса) —
вместо пересканирования всей цепи на каждый блок. При их отсутствии верификатор
строит контексты сам (O(n) на вызов — приемлемо для WS/commit).

## Активация: env `AGT_CORE_P0_HEIGHT`

По образцу `AGT_MGNT_HEIGHT`:

- не задан / `0` / мусор → **выключено** (чистое legacy-поведение, ноль изменений для
  работающих нод и исторических цепей);
- задан `N ≥ 1` → строго новые правила для блоков высотой **≥ N**.

**Ретроспектива запрещена физически:** историческая цепь полностью валидна в
legacy-режиме (проверено: `validate(true)` на копии живой цепи до h=9263 — ok,
0 отрицательных балансов, supply 463 100), но при пороге = 1 эта же цепь падает на
`coinbase_txid_not_canonical` (старые coinbase имели txid `coinbase-<ms>`). Поэтому
активация — ТОЛЬКО на будущую высоту, порядок ниже.

## Точки входа, покрытые единым верификатором

| вход | файл | вызов |
|---|---|---|
| HTTP `/block/submit`, `/mine` | node.mjs | `commitMinedBlock` → `validateBlockAgainstChain` |
| WS-приём блока (2 обработчика) | node.mjs | `validateBlockAgainstChain` |
| линейный синк и re-org | sync.mjs | `validateBlockAgainstChain` (инкрементальные контексты) / `adoptFork` |
| полная историческая сверка | core.mjs | `validate(true)` → тот же верификатор по каждому блоку |

## План активации (chekcpoint) на основной сети

1. Слить PR с этим кодом в main; убедиться, что CI зелёный и все четыре ноды
   перезапущены на новый код **до установки порога** (пока env не задан, все ноды
   работают по-старому — никакой несовместимости).
2. Снять живой tip у основного издателя: `GET /info` → `blocks` = H_now.
3. Выбрать порог с запасом: `AGT_CORE_P0_HEIGHT = H_now + 30` (~15 минут при
   30 с/блок).
4. Прописать `set AGT_CORE_P0_HEIGHT=<N>` в `run-node.cmd`, `run-node2.cmd`,
   `run-node3.cmd`, `run-node-ts.cmd` И на VPS (`deploy-vps.sh` / systemd `Environment=`) —
   у ВСЕХ нод одно и то же N, прежде чем любая нода достигнет N.
5. Перезапускать ноды штатными обёртками (точный PID → старт обёртки), сверить
   `/life`: `fresh=true`, `chainValid=true`.
6. Смотреть переход порога N: на первых ≥ N блоках обязательный канонический
   coinbase; при конфликте сверять по `/blocks` — строгая нода пишет точную причину
   (`тезис: reason` в логе `[ws] блок ... отвергнут`).
7. После перехода — контрольные прогоны: `test/core-p0.mjs` (26 пунктов),
   `validate(true)` по chain.json — `ok=true, negativeBalances=0`.
8. Следующий раунд усиления включается тем же координированным способом.

Запрещено: активация ретроспективно (порог < текущего tip), включение без
координации всех нод, изменение исторических блоков.

## Ограничения (честно)

- `mineOnce` (соло-путь ноды) по прежнему не валидирует свой блок перед push
  (доверенный внутренний путь); все ВНЕШНИЕ входы валидируются.
- Формат fork-атаки из `p2p/fork-attacker.mjs` после активации перестанет
  приниматься — это отдельный проверочный инструмент, его правку не делал.
- Защита от овердрафта между блоками существует и раньше (addTransaction), но
  блок могла обойти только минер; теперь закрыт и блочный путь (fraud-минёр).
