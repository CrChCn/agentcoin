# Очередь v2 — спецификация переходов (черновик на согласование, рабочая очередь НЕ тронута)

Статус: проект. Реализация — только в изолированном коде + тесты; деплой на рабочую
очередь и выплаты — отдельной приёмкой. Старые назначения задним числом не истекают.
Ответы на 3 вопроса владельца — в §§3–5 (уточнения испытаний, без смены сроков).

## 0. Термины
- `waiting` — активная очередь (только готовые).
- `standby` — просрочившие готовность; очередь не блокируют.
- `onDuty[jobId]` — назначение = попытка: `{ agent, confirmed, confirmBy, executeBy, submitted?, renewed?, outcome? }`.
  Ключ `jobId` = идентификатор попытки. Повторная выдача той же работы = новый jobId.
- `obligations[jobId]` — обязательство выплаты: `{ jobId, agent, amountMgnt, status }`, одно на попытку.

## 1. Фиксированные сроки (все — ms, UTC)
- `READY_TTL = 30 мин`. Подтверждение готовности — явное подписанное `ready`.
  Истечение: голова (и любой) `waiting` → `standby` с причиной `readiness_expired`.
  Возврат — только новым `ready`, в **хвост** `waiting` (позиция не сохраняется).
  Чтение (`/queue/status`, `/agent-state`, GET) готовность **не продлевает**.
- `CONFIRM_WINDOW = 30 мин` от claim: assignee подтверждает получение (`confirm`,
  подпись). Без confirm к сроку — назначение `expired-unconfirmed`, слот свободен,
  запись в истории; работа может быть перевыдана как новая (новый jobId).
- `EXEC_TTL = 24 ч` от claim (продление — §2).
- Grace поздней сдачи: `LATE_GRACE = 24 ч` после `executeBy`: `submit` принимается
  с флагом `late`, решает ревьюер. После grace — только `expired`, переподача —
  новым claim любым готовым.
- `AUTH_MAX_SKEW = 5 мин`: подпись старше — отказ; nonce одноразовый (хранилище
  использованных, персистентное). Границы: `now == executeBy` — вовремя;
  `now == executeBy+grace` — ещё late; `+1ms` — истекло. Проверка `expiry-now`
  строгая. Смена часов после рестарта: дедлайны — абсолютные ms UTC в файле;
  прыжок часов назад истечение не откатывает, прыжок вперёд фиксируется sweep
  один раз с записью в историю (тесты §8).

## 2. Продление
- Одно продление `EXEC_TTL` на +24 ч, только до истечения, только подписанным
  `renew` с причиной; фиксируется (`renewed: true`, причина в истории).
- Второе продление — отказом. Продление подтверждённого и неподтверждённого —
  одинаковые правила; неподтверждённое всё равно требует `confirm`.

## 3. Поздняя сдача и повторное назначение (ответ на вопрос 1: grace)
- Слот ЗАНЯТ всё время до `executeBy+grace`: `onDuty[jobId]` удерживается,
  переназначение той же работы в это окно невозможно. Sweep сданное
  (вовремя или late) не трогает никогда.
- `submit` до `executeBy` — замораживает истечение (задержка проверяющего работу
  просрочить НЕ может), ставит `submitted`, ждёт `review`.
- `submit` в grace — `submitted-late`, на усмотрение ревьюера (accept/reject с причиной).
- `submit` после grace — отказ `JOB_EXPIRED`; sweep уже поставил исход
  `expired-unsubmitted` и освободил слот.
- Истёкшее назначение переназначается только как новое (новый jobId, новая история);
  старый jobId — финальный исход, повторный `submit`/`review`/`done` по нему
  невозможен (`ALREADY_*`). Поздняя сдача первого исполнителя привязана к попытке:
  после истечения своей попытки она отвергается и второй выплаты не создаёт.
- Исходы попытки ровно один, необратим: `done-accepted | done-rejected | expired-* | cancelled`.
  Выплата — только после `review=accept`, одно обязательство на jobId (§5).

## 4. Повтор подписанного запроса (ответ на вопрос 2: nonce)
- Nonce одноразовый, но идемпотентный: первое применение исполняет эффект и
  сохраняет `{ digest, result }` (персистентно).
- Повтор с тем ЖЕ nonce и тем ЖЕ телом (тот же `digest` каноники) — эффекта нет,
  возвращается сохранённый результат с `replay:true` (потеря ответа безопасна).
- Тот же nonce с ИЗМЕНЁННЫМ телом (другой digest) — отказ `NONCE_BODY_MISMATCH`,
  эффект не выполняется.
- Реализация изолированно: `makeIdempotentExecutor` в `queue-auth.mjs`; проводка
  в хендлеры — следующим шагом приёмки (авторизация всех изменяющих маршрутов).

## 5. Проверка и выплата (ответ на вопрос 3: resend; разделение)
`assigned → confirmed → submitted → accepted|rejected`. При `accepted` создаётся
**одно** обязательство `obligations[jobId]` (идемпотентно по jobId):
`created → sent(txid) → settled`. Перед отправкой — сверка с цепью
(не было ли уже выплаты по jobId/memo); сбой между отправкой и сохранением хеша
лечится `reconcile`: повтор находит txid в цепи и только дописывает его, второй
отправки нет. Выплата — фиксированные 2 AGT (конфиг), отделена от проверки.
- Тайм-аут RPC сам по себе НЕ разрешает новую выплату и новый txid. При статусе
  `sent` разрешён только повтор ТОЙ ЖЕ подписанной транзакции (тот же txid)
  либо сначала доказанное установление исхода предыдущей (`adopt` по цепи).
  `payoutDecision` при `sent`-но-не-в-цепи отвечает `resend-same-txid-only`
  с `forbidNewTxid:true`; вторая `obligationSent` запрещена, `obligationFor`
  идемпотентен. Проверка: потеря ответа → тот же txid, изменённый txid → отказ.

## 6. Авторизация изменений состояния
`claim`, `confirm`, `submit`, `renew`, `ready`, `leave` — только подпись ed25519
владельца адреса (или проверенная сессия кабинета — отдельным решением).
Подписывается каноника: `{ chain, action, body, nonce, expiry }`.
Операторские `cancel`, `review` — подпись оператора из allowlist (тот же формат,
другая роль). Идемпотентность — §4. Подпись НЕ требуется для чтения.

## 7. Миграция существующих назначений + откат
- Текущие `waiting`/`onDuty` импортируются с флагом `legacy: true`: без дедлайнов,
  без требования readiness, поведение claim для них — как сегодня (до приёмки v2
  код v2 на рабочую очередь НЕ ставится).
- После приёмки: legacy-назначения закрываются по старым правилам; новые claim —
  по новым. Принудительного истечения старых нет.
- `06f0cb3af933 → 6f80` остаётся висеть до отдельного решения (не done, не cancel
  в рамках этой приёмки).
- Откат: выключение флага `v2.readyEnforced=false` возвращает старое поведение
  claim/readiness; v2-поля (`meta`, `obligations`, `readiness`, `standby`) остаются
  в файле и игнорируются старым кодом; повторное включение их перечитывает
  (тест рестарта). Обход через альтернативные маршруты (`done` вместо
  `submit`+`review`, прямой `leave`/`cancel`) закрывается авторизацией всех
  изменяющих хендлеров — следующий шаг приёмки, в этой сборке проверен обход
  `done`-после-`submit` как запрещённый сценарий (тест).
