# C2 — установка на отдельный ops-host без настоящих агентов

Цель C2: постоянный сервис с очередью, планировщиком, watchdog, памятью и
read-only API на **отдельном** хосте. Настоящие агенты, deployer, Caddy и
production остаются выключенными.

Состояние C2 после локальной приёмки:

| Пункт | Состояние |
|---|---|
| allowRealAgents | `false` |
| deployer | disabled (юнит под `ConditionPathExists`, скрипт отказывает кодом 3) |
| Caddy route | отсутствует |
| API | только `127.0.0.1` и `::1` |
| planner/checks | работают, пустой backlog → IDLE |
| queue | сохраняется между процессами |
| STOP | ставит и снимает только оператор |
| Код | root-owned, read-only, отдельно от данных |
| Установка на реальный хост | **выполнена 2026-11-21** на node1 (`2.31.145.160`), см. §2.1 |

Локально доказано 28 проверок (`evidence/c2-acceptance.json`), включая
совпадение манифеста с фактическим владельцем данных, два пункта
требуют реального хоста: `systemctl is-active` и поведение после reboot.

## 1. Раскладка

```
/opt/agentcoin-orchestrator/
├── releases/<UTC timestamp>/orchestrator/   root:root, 0555, неизменяем
└── current -> releases/<...>                root:root

/var/lib/agentcoin-orchestrator/            agt-orchestrator:agt-orchestrator
├── queue/{queue.json,tasks,backlog,registry.json,mission.json,incidents.json}
├── project-memory/  runs/  artifacts/  state/  workspaces/
└── control/STOP                              root:root 0755 — сервис не пишет

/var/log/agentcoin-orchestrator/            agt-orchestrator
/etc/agentcoin/ops.env                      root:agt-orchestrator 0640
/etc/agentcoin/operator.key                 root:root 0600 (приватный ключ STOP)
```

Юниты получают `ReadWritePaths` только для data и logs; код и управляющий
каталог — под `ReadOnlyPaths`. Ни один юнит не может изменить собственный код.

## 2. Установка

```bash
# 1. Проверить план (ничего не меняет)
./service/install.sh --dry-run

# 2. Установить код, данные и юниты (root)
sudo ./service/install.sh

# 3. Один раз создать операторский ключ и опубликовать его публичную часть
sudo node /opt/agentcoin-orchestrator/current/orchestrator/service/operator.mjs \
  init-key --root /var/lib/agentcoin-orchestrator

# 4. Запустить сервисы
sudo ./service/install.sh --enable
```

`install.sh` создаёт `releases/<ts>` с SHA256-манифестом
(`/var/lib/agentcoin-orchestrator/inventory/install-manifest-<ts>.json`), где
`serviceUser`/`deployUser` передаются из `SERVICE_USER`/`DEPLOY_USER` явно и
юниты получают те же `User=`/`Group=`. После записи установщик читает манифест
обратно и сверяет `serviceUser` с фактическим владельцем `/var/lib/...`:
расхождение — отказ кодом 83. Поле `dataOwner` фиксирует владельца с диска
(в `--prefix`-репетиции это вызывающий пользователь, `mode: rehearsal`),
переключает `current` атомарно, не перезаписывает `queue/`, `mission.json`,
`registry.json` и `project-memory/`, отказывает при чужом владельце данных
(код 79) и при control-каталоге, доступном на запись группе (код 82).

Граница `--prefix`: репетиция проверяет раскладку, права на код, манифест и
rollback/uninstall, но не создаёт пользователей, не делает `chown`, не вызывает
systemd и помечает манифест `mode: rehearsal`; `--enable` с `--prefix` — отказ 64.
Реальные `User=`, владельца данных и `systemctl is-active` доказывает только
`service/tools/c2-host-acceptance.sh` на хосте.

Откат и снятие:

```bash
sudo ./service/install.sh --rollback          # предыдущий release, данные не трогает
sudo ./service/install.sh --uninstall         # снять код и юниты, данные остаются
```

### 2.1 Фактическая установка на node1 (2026-11-21)

Хост: `agentcoin.work` / `2.31.145.160`, Ubuntu 24.04.4.

| Что | Факт |
|---|---|
| runtime | `node` v24.22.2 в PATH симлинками `/usr/local/bin/{node,npm,npx,corepack}` → `/opt/agentcoin-staging/runtime/node-v24.22.2/bin/*` |
| sandbox | `bubblewrap 0.9.0`; без профиля AppArmor userns запрещён (`kernel.apparmor_restrict_unprivileged_userns=1`), поэтому добавлен `/etc/apparmor.d/bwrap` (`flags=(unconfined)` + `userns,`) — `bwrap --unshare-all` под uid 65534 проходит |
| release | `/opt/agentcoin-orchestrator/releases/20261121T152226Z`, 138 файлов, `current` переключён атомарно |
| данные | `/var/lib/agentcoin-orchestrator`, владелец `agt-orchestrator`, `control/` — `root:root 0755` |
| ключ | `/etc/agentcoin/operator.key` 0600, `state/operator.pub` `root:agt-orchestrator 0640`, keyId `7bcc357f54da5900` |
| юниты | `agt-orchestrator`, `agt-orchestrator-api`, оба таймера — active; `agt-deployer` — inactive (`ConditionResult=no`) |
| API | `127.0.0.1:8799` и `[::1]:8799`, `/ops/status` 200, `/ops/health` 200 |
| публикация | Caddy `handle /ops` (статика) и `handle /ops/status` → `127.0.0.1:8799`; снаружи `/ops` 200 (9 029 Б), `/ops/status` 200 `application/json` |
| access log | `log`-блок в site-блоке, `/var/log/caddy/access.log` `caddy:caddy 0640`, JSON, 50 MiB × 10 |

Найдено и исправлено при установке: `service/ops-env.example` задавал
`OPS_ROOT=/srv/agentcoin-ops`; `EnvironmentFile` в systemd перекрывает
`Environment=` из юнита, поэтому оба сервиса падали с
`ENOENT … /srv/agentcoin-ops/queue/tasks`. Пример исправлен на
`/var/lib/agentcoin-orchestrator`, файл на хосте тоже.

`/var/log/caddy/access.log` создаётся первым `validate`/`reload` от root,
поэтому после появления файла нужен `chown caddy:caddy` — иначе reload
отвечает 400 `permission denied`.

Третья правка — `watchdog.mjs`: проверка `DUPLICATE_INSTANCE` сравнивала pid из
heartbeat с `process.pid` самого watchdog, а он по конструкции отдельный
процесс, поэтому тревога срабатывала всегда (`verdict: attention`, юнит
`status=2` на каждом тике). Теперь вызов `opsd watchdog` идёт с
`standalone: true`, и дубликат проверяется только внутри оркестратора.

## 3. STOP и resume — только оператор

Сервис читает `control/STOP`, но не может его создать или удалить: каталог
принадлежит root, а приватный ключ подписи лежит в `/etc/agentcoin/operator.key`
(0600). События `service.stop_signed` / `service.resume_signed` подписаны
Ed25519; сервис проверяет их публичным ключом `state/operator.pub`.

```bash
sudo node .../service/operator.mjs stop   --root /var/lib/agentcoin-orchestrator --reason "maintenance"
sudo node .../service/operator.mjs resume --root /var/lib/agentcoin-orchestrator
sudo node .../service/operator.mjs verify --root /var/lib/agentcoin-orchestrator
```

`opsd resume` всегда завершается кодом 78: компрометация оркестратора не даёт
возобновить работу. Неподписанного пути нет и для STOP: `opsd stop` отвечает
`STOP_REQUIRES_OPERATOR` кодом 78 и не создаёт файл — метода, пишущего STOP,
в сервисе больше не существует.

## 4. Pinned runtime для будущего C3

Codex ставится один раз из готового каталога в постоянное место, без `/tmp` и
без домашних каталогов:

```bash
sudo node .../service/tools/codex-pin.mjs pin \
  --from /root/codex-0.171.0 --version 0.171.0 \
  --base /opt/agentcoin-ops/runtime
sudo node .../service/tools/codex-pin.mjs verify \
  --root /opt/agentcoin-ops/runtime/codex-0.171.0 --check-binary
```

`pin` отказывает для временных путей (код 65), существующий runtime не
перезаписывает (73), снимает биты записи и пишет `manifest.json` с SHA256;
`verify` проверяет версию, хеши, root-ownership, отсутствие записи группе и
`autoUpdate=false`. `CODEX_HOME` — отдельный каталог сервиса.

Включение настоящих агентов требует одновременно:

1. `adapterEndToEnd=true` и `blockers=[]` из `tools/agent-hostile-check.mjs --real`;
2. `opsd runtime` → `ok: true`;
3. `mission.allowRealAgents=true` — отдельным решением владельца.

## 5. Приёмка на хосте

Локально (репетиция, без root):

```bash
node service/tools/c2-acceptance.mjs /tmp/c2-accept
```

На ops-host после установки автоматическая часть (пишет
`evidence/c2-host-acceptance.txt` и `.json`, PASS только за выполненную проверку):

```bash
# 1. юниты, код, deployer (безопасно, ничего не меняет)
sudo ./service/tools/c2-host-acceptance.sh

# 2. внешний отказ API: зонд на другой машине, результат переносится на хост
./c2-host-acceptance.sh --probe-remote=<ops-host>:8799 --probe-out=probe.json
scp probe.json <ops-host>:/tmp/probe.json
sudo ./service/tools/c2-host-acceptance.sh --external-probe=/tmp/probe.json

# 3. STOP и reboot: два прохода
sudo ./service/tools/c2-host-acceptance.sh --stop-and-reboot
sudo reboot
sudo ./service/tools/c2-host-acceptance.sh --after-reboot

# 4. rollback и uninstall — в самом конце
sudo ./service/tools/c2-host-acceptance.sh --with-teardown
```

Скрипт проверяет только хостовые пункты; локальные (IDLE, одна задача по
registry evidence, symlink, инциденты, подписи, allowlist API, runtime) остаются
за `c2-acceptance.mjs` и здесь не дублируются. Без зонда пункт `external-refusal`
остаётся `PENDING`, а не `PASS`.

То же самое глазами, без скрипта:

```bash
systemctl is-active agt-orchestrator.service agt-orchestrator-api.service \
  agt-orchestrator-scheduler.timer agt-orchestrator-watchdog.timer
find /opt/agentcoin-orchestrator/current -type f -perm -u+w    # пусто
systemctl show -p ConditionResult --value agt-deployer.service  # no
cat /var/lib/agentcoin-orchestrator/control/STOP               # есть после reboot
```

Результат скрипт дописывает в `evidence/c2-host-acceptance.txt` (и `.json`, по
строке на прогон); локальные пункты остаются в `evidence/c2-acceptance.txt`.

## 6. Что ещё не доказано

- реальные `systemctl is-active`, reboot и внешний сетевой отказ — требуют
  отдельного хоста; локальный харнесс помечает их `PENDING`, а не `PASS`;
- настоящий Codex+bwrap crash-recovery остаётся обязательным gate перед C3
  (`service/tools/c1-real-crash-recovery.sh`, сейчас `BLOCKED`: CLI отсутствует);
- Caddy и публичный `/ops`: выложены 2026-11-21 (`/ops` 200, `/ops/status`
  200 через `reverse_proxy`); страница `site/ops.html` и маршруты в
  `caddy-routes.conf` совпадают с прод-Caddyfile.
