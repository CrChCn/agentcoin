# AGENTCOIN → Proof of Useful Work: исследование и план

Дата: 2026-11-07. Статус: план, код не менялся.

## 1. Что изучено

### Proof of Useful Work (PoUW)

PoUW: энергия, securing-сеть, одновременно даёт независимо ценный результат
(AI-инференс, ZK-пруфы, оптимизация, рендеринг). Три жёсткие проблемы, на которых
ложатся почти все проекты:

1. **Асимметрия верификации.** SHA-256 проверяется одним хэшем. У инференса/фолдинга/
   обучения проверка стоит почти как сама работа, а мусор выглядит правдоподобно.
   Рабочие дизайны берут задачи с дешёвой проверкой: умножение матриц (проверка
   Фрейвалдса), оптимизационные задачи (значение целевой функции проверяется дёшево),
   ZK-пруфы (верификация — миллисекунды, генерация — минуты).
2. **Стыковка спроса и предложения.** PoW-майнеру всегда есть что майнить. PoUW-майнеру
   нечего делать без внешнего спроса → майнеры уходят → падает безопасность.
   Все проекты годы субсидируют одну из сторон эмиссией.
3. **Читерство.** Эмпирическое исследование Pearl (2026, arXiv:2606.04819): сеть
   24 EH/s (~320k GPU) производила **ноль** полезного AI-компута — доминирующий
   майнер не содержал инференс-кода, а протокол верификации принимал случайные
   матрицы. Урок: статистические проверки бьются, нужны криптографические.

Выживший паттерн (Simback, 2026): **цепь — «бригадир маркетплейса», а не исполнитель.**
Обычный (часто PoS-)чейн рядом: публикует задания, раздаёт воркерам, проверяет
результаты, платит. Полезная работа выполняется off-chain, консенсус остаётся простым.
Примеры живьём: HyperCycle (ноды исполняют агентские вычисления, берут fee),
Pocket Network (pay-per-call, поставщик держит серверы), AI Power Grid (воркеры
получают AI-задачи, платят почасово за den work units), modelOS (AuxPoW: одна работа —
две награды), Operon (ноды НЕ гоняют AI, а держат протокольный слой: аттестатинг,
реестр, роутинг, метринг — лёгкий, детерминированный, проверяемый).

### Agent-as-a-Node

Два смысла, оба применимы:
- **A. Агент как оператор ноды.** LLM-агент держит кошелёк, принимает экономические
  решения (EconAgentic, 2025: агенты реагируют на стимулы, входят/выходят по
  прибыльности), запускает/настраивает инфраструктуру, выполняет задания за токены.
- **B. Нода как исполнитель агентских нагрузок.** Сеть продаёт compute/attestation/
  routing; операторы зарабатывают с каждого вызова (HyperCycle Node Factories,
  OptimAI Core Nodes, Origins Network).

## 2. Вердикт для AGENTCOIN: да, гибридом, PoW не трогать

Заменять `hashMeetsDifficulty`/`expectedDifficultyBits`/выбор ветки по work — нельзя:
там боевая антифорк-механика (пининг сложности, miner-guard, `multiple_coinbase`,
`coinbase_inflation`), её переписывание = новая поверхность атаки.

Но **70% PoUW уже построено**: джобборд с эскроу (`escrowopen → job-claim →
escpayout:/escrefund:`), казна с комиссией 4.525 AGT, паспорта-идентичности,
`miner-client.mjs` (внешние майнеры уже берут template и считают), gov-пропозалы.
Правильный ход — надстроить «бригадира маркетплейса» над существующим эскроу,
а консенсус оставить как есть (фазы 1–2 вообще без изменений консенсуса).

Почему первым шагом именно **проверка ZK-доказательств**:
- Верификация Groth16/PLONK **детерминирована и стоит миллисекунды** — любой узел
  перепроверяет результат почти бесплатно. Проблема №1 (асимметрия) решена
  математикой, а не доверием; избыточные вычисления и сэмплинг не нужны вообще.
- В отличие от инференса, ответ бинарен (valid/invalid) — нет споров о качестве.
- `snarkjs` — чистый JS, ставится в `node.mjs` без нативных зависимостей.
- Якорение хэша проверенного пруфа в цепи даёт проверяемый след полезной работы
  (будущие «useful-work receipts»).

## 3. План по фазам

### Фаза 0 — ZK-verify как эскроу-задача (без изменений консенсуса)

Новые сущности поверх существующего джобборда:

1. `POST /jobs/compute` — заказчик публикует `{ kind:'zkverify', circuit, vk,
   publicInputs, proof, bounty }`. Бounty замораживается в эскроу, комиссия — в казну
   (тот же сплит, что сейчас).
2. Майнер-агент (смысл A) забирает открытые `zkverify` с джобборда, гоняет
   `snarkjs.groth16.verify(vk, publicInputs, proof)` локально, шлёт claim-tx
   `zkclaim:{ escId, valid:true/false }`.
3. Нода перед приёмом claim **сама перепроверяет пруф детерминированно**
   (миллисекунды) — ложный claim невозможен by construction, честный всегда
   проходит. Доверия к воркеру не требуется.
4. Выплата — существующим `escpayout:`; хэш пруфа + `valid` пишутся в memo/индекс
   цепи (якорь, пригодится в фазе 2).
5. Тесты: юнит на детерминизм (один пруф → N нод, один вердикт), e2e «заказ →
   claim → payout», отрицательный (поддельный пруф → claim отвергнут, bounty цел).

Критерий готовности фазы: 10 реальных `zkverify`-сделок через эскроу, 0 споров,
медиана verify < 50 мс на ноде.

### Фаза 1 — роли нод (Agent-as-a-Node, смысл B)

- Формализовать три роли: **Validator** (консенсус, как сейчас), **Worker**
  (берёт compute-задачи, паспорт + стейк/репутация — гейт от сибилов),
  **Gateway** (публичные API, как node1-3 сейчас).
- Репутация воркера = закрытые bounty + отсутствие rejected-claim; роутинг жирных
  задач — по репутации; скоринг виден в `/jobs/workers`.
- Биллинг уже есть (AGT-микроплатежи через эскроу); добавить почасовые/поштучные
  тарифы в карточку воркера (пример AI Power Grid: pro-rata за work units).

### Фаза 2 — полезная работа влияет на майнинг (мягкая связь, консенсус цел)

- «Useful-work receipts»: coinbase-поле/расширение заголовка `workRoot` — корень
  дерева хэшей проверенных (фаза 0) работ, включённых майнером.
- Блок с непустым валидным `workRoot` получает **приоритет мемпула и +fee-бонус
  из казны** (gov-параметр), но валидность PoW не меняется: старый майнер без
  работ по-прежнему валиден. Стимул без хардфорка.
- Метрика сети: `usefulWorkPerBlock`, дашборд «сколько пруфов проверено за AGT».

### Фаза 3 — (опционально, только при живом спросе) жёсткий PoUW

Только если фазы 0–2 дадут устойчивый внешний спрос (иначе — проблема №2 убьёт
безопасность): рассмотреть AuxPoW-вариант (как modelOS: одна работа — награды
сразу двух типов) или NoisyGEMM-подобное ядро. Отдельный AGIP, тестнет, аудит.
Без спроса — не делать.

## 4. Чего НЕ делать

- Не заменять PoW на «проверку инференса» (недетерминировано → нужны избыточные
  вычисления/сэмплинг → Pearl-урок).
- Не верить статистическим проверкам (Фрейвалдс без рандома от цепи, «похоже на
  инференс») — только криптографические.
- Не субсидировать спрос из казны дольше фазы 0 без метрик (ловушка проблемы №2).

## 5. Первый конкретный шаг (оценка: 1–2 вечера)

1. `core.mjs`: `verifyZkClaim(claim, escrowView)` — чистая функция, snarkjs под капотом.
2. `node.mjs`: роут `POST /jobs/compute` (freeze bounty) + приём `zkclaim` в `/tx`
   через `verifyTxAny`-роутер (там уже есть место).
3. `miner-client.mjs`: режим `--compute` — опрос `/jobs/state?kind=zkverify`,
   verify локально, отправка claim.
4. Тест `test/pouw-zkverify.mjs` по образцу `core-p0.mjs` + 3 e2e-сделки на node2.
5. AGIP-запись: параметры (fee %, лимит размера пруфа, allowlist circuits v0).
